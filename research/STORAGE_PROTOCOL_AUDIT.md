# Follow-up source audit: persistence prerequisites

Date: 2026-09-29 UTC. Authoritative implementation revision: `472f69313a7bd563786f5e2e6c9a2af3d5c1d3cc`. The live PR head was rechecked and was unchanged. This audit narrows three prerequisites from speculative risks to directly observable source defects or missing behavior.

None of the findings below proves the cause of the J293 master Catacomb status `0x6`. They should be addressed before interpreting hardware persistence experiments.

## A. Open errors incorrectly become permission to create an identity

Evidence chain:

1. `drivers/soc/apple/store_shim.c` calls `open_as_kernel()` and converts **every** `IS_ERR(f)` result to NULL in the regular-file open helpers.
2. `drivers/soc/apple/shim.rs::StoreFile::open_readonly()` converts any NULL to `ENOENT`.
3. `drivers/soc/apple/keybag.rs::read()` returns `State::Absent(NoStoredKeyBag)` on `ENOENT`, explicitly intending all other failures to be fatal.
4. `sks.rs::sks_provision_identity_keybag()` consumes that absence proof. A later successful intent write could replace existing state before a new provisioning attempt.

Thus a transient EIO/ENOMEM or other non-missing-file open error is indistinguishable from no existing identity. A persistent access failure might prevent the next write too, but that does not rescue the invariant: the code has authorized creation based on a false absence proof. Actual hardware data loss was not tested or claimed.

### Candidate implementation

[store-open-errors.patch](../proposals/store-open-errors.patch) preserves Linux error pointers through the C boundary and adds `sep_store_open_error()` so Rust constructs a `StoreFile` only after checking the original errno. It also distinguishes an invalid block device from a read-only block device. All four Rust open methods use one decoding function. Unexpected NULL returns EIO rather than absence.

The snapshot remains immutable. The patch is generated by [build-storage-candidate.py](../proposals/build-storage-candidate.py), and `git apply --check` succeeds against the pinned source. It must still be compiled in the full kernel tree, checked for exported prototype/FFI consistency, and reviewed for all callers. The patch changes no firmware commands or storage format.

### Verification performed

[test_storage_open_errors.py](../proposals/tests/test_storage_open_errors.py) extracts the actual original and candidate C regular-file open helpers, compiles them with a mock `open_as_kernel`, and injects eight errors across three open operations:

`ENOENT`, `EIO`, `EACCES`, `ENOMEM`, `ELOOP`, `ENOTDIR`, `EROFS`, `ENOSPC`.

All **24 error cases plus 3 successful opens** pass; unexpected NULL separately maps to EIO. The original helpers return NULL for all injected failures, reproducing the loss of error identity. The Rust wrapper change is source-reviewed, **not compiled**, because Rust is not installed. The block-device branch is source-reviewed but not exercised by this harness. Tests use temporary files and an ordinary C compiler; no real block device or SEP is opened.

Full integration acceptance must inject failures at the real VFS/FFI boundary and prove that only a genuine ENOENT authorizes the initial-create path. It must also prove that an error pointer never reaches file-size/read/close operations.

## B. A refused-create marker bypasses integrity validation

SOURCE: `keybag.rs::read()` checks magic and format version, then immediately returns `State::Absent` when `state == STATE_REFUSED`. Length, UUID, secret and CRC validation occur only later for committed records. The normal `mark_refused()` writer emits a canonical empty record, but the reader does not verify that shape before authorizing another create.

A malformed record with matching magic/version and a state word equal to 2 is therefore accepted as proof of absence even if its checksum is wrong or its body still describes an existing identity. This is a source control-flow finding; no real keybag was modified.

### Implementation specification

Before returning absence for a refused marker, require:

- Exactly the canonical header size, with no trailing data.
- Zero wrapped length, zero secret length and the writer's zero UUID.
- Reserved bytes in their supported representation.
- The existing CRC over the canonical `(VERSION, STATE_REFUSED, lengths, UUID, empty body, empty secret)` input, using the existing format's byte order.
- A recognized format version, already checked by the current reader.

Any discrepancy returns a corruption/error state and preserves the artifact. Do not modify the existing on-disk format merely to fix validation. CRC is corruption detection, not protection against a privileged adversary rewriting both record and checksum. Production provenance still depends on protected host storage and the enclave protocol.

Required tests: canonical refused marker accepted; nonzero body/secret/UUID, wrong CRC, truncation, trailing bytes and unknown state rejected; committed records unchanged; intent state remains ambiguous and never becomes absence. The final fix should extract a pure byte parser testable independently of hardware and preserve the typed `NoStoredKeyBag` gate.

## C. The stable OS UUID fallback is declared but not implemented

The local inventory shows `/chosen/apfs-preboot-uuid` absent. In the pinned source:

- `profile.rs` declares `IdentitySource::HostPersisted` and selects it for T6020.
- No consumer of `profile.identity` was found in the retrieved driver sources.
- `sep.rs::prepare_os_uuid()` handles only explicit `os_uuid_hi`/`os_uuid_lo` parameters or `dt::preboot_uuid()`.
- If both are unavailable, it sets `os_uuid=None`.
- `xarm.rs` answers `GET_OS_UUID` with `STATUS_UNAVAILABLE` when that value is None.
- No implementation of an `aurora-sep-os-uuid.bin` read/create path appears in this snapshot.

The earlier proposal to retain a stable fallback must therefore be read as **work to implement**, not a working capability of the pinned tree. Reports from differently assembled branches that persist an OS UUID do not prove this head does.

### Two implementable approaches

**Preferred short-term experiment: loader-managed stable identity, using the existing module parameters.** This avoids changing the SEP wire protocol and permits ordinary userspace durable-file operations.

1. Before initial provisioning, choose either the existing authoritative preboot UUID or an explicitly initialized Linux identity. Do not replace an existing identity after fingerprints/keybags have been created.
2. Persist a generated 16-byte UUID once in a root-owned protected file. Use initialized OS randomness. Publish with no-clobber creation and fsync of both file and directory before loading the driver; incomplete/corrupt files are errors, not permission to regenerate.
3. If the identity file is missing while any identity bag, Catacomb, reference key or host-state artifact exists, stop and reconcile the original identity. Do not infer a replacement from a random newly generated value.
4. Decode the bytes into two **big-endian** u64 values: `hi=int.from_bytes(uuid[0:8], 'big')`, `lo=int.from_bytes(uuid[8:16], 'big')`. This matches the kernel's `to_be_bytes()` reconstruction. Treat all-zero as invalid because it selects the “no explicit override” branch.
5. Supply those parameters through the same single authoritative options path as writes/provisioning controls. Do not append duplicate module parameters to modprobe.d entries. Keep the identity stable across restarts and package upgrades.
6. Record privately whether identity came from firmware or Linux provisioning. Reject conflicting sources instead of selecting whichever is most convenient that boot.

**Long-term alternative: implement `IdentitySource` inside the driver** using the corrected errno-preserving storage API, durable identity creation and explicit migration rules. This centralizes policy but requires careful kernel file-access, mount-timing and crash-handling review. Do not implement it by reusing an unchecked NULL-to-ENOENT helper.

Acceptance: absent firmware UUID plus initialized host identity produces a consistent GET_OS_UUID reply across boots; unreadable/missing-after-provision/corrupt host identity refuses provisioning; repeated startup never creates a new identity; parameter byte-order round-trip is exact; explicit configuration cannot override a different existing identity silently.

## D. Exact save/confirmation boundary for the next trace

`sbio.rs::save_catacomb()` currently performs:

1. SAVE_CATACOMB request for one component.
2. Validate response status, payload size and carried user ID.
3. Write and fsync that component's opaque host file.
4. CONFIRM_SAVE request.
5. Return true only if confirmation succeeds.

This is a useful baseline: it already confirms after a durable per-file write. Do not replace it with “confirm before storing” to make a refusal disappear. However, there is no transaction spanning all component files and keybag snapshot state. A failure after the user component succeeds but before the master save leaves a partially advanced generation; automatic retries must not treat it as a pristine enrollment.

The next metadata trace should distinguish **SAVE refusal** from **CONFIRM refusal**, and record component state before SAVE, after SAVE, after durable host write and after CONFIRM. The reported J293 failure is at the master's SAVE, after the user's save/confirmation path. That makes the user-to-master transition and bag/context generation more discriminating than another broad command sweep.

## Effect on the main research conclusion

These findings add concrete prerequisite fixes and improve the experimental design. They do not prove a working J293/15.3.1 persistence solution. That goal remains open until the correct firmware sequence and the integrated implementation are demonstrated.
